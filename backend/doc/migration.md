การจัดการ Database Migration

ภาพรวม

Database Migration คือกระบวนการจัดการการเปลี่ยนแปลงโครงสร้างฐานข้อมูล โดยบันทึกการเปลี่ยนแปลงแต่ละครั้งแยกตามเวอร์ชัน เพื่อให้สามารถตรวจสอบ ติดตาม และควบคุมโครงสร้างฐานข้อมูลได้อย่างเป็นระบบ

Migration ช่วยให้ฐานข้อมูลในแต่ละสภาพแวดล้อม เช่น Development, Testing และ Production มีโครงสร้างที่สอดคล้องกัน

1. วัตถุประสงค์

จัดการเวอร์ชันของโครงสร้างฐานข้อมูล

ติดตามประวัติการเปลี่ยนแปลงฐานข้อมูล

ลดความผิดพลาดจากการแก้ไขโครงสร้างฐานข้อมูลด้วยตนเอง

ทำให้สามารถสร้างฐานข้อมูลใหม่ตามโครงสร้างที่กำหนดไว้

รองรับการย้อนกลับการเปลี่ยนแปลงเมื่อจำเป็น

2. หลักการทำงาน

Migration จะแบ่งการเปลี่ยนแปลงออกเป็นไฟล์ตามลำดับเวอร์ชัน โดยแต่ละไฟล์จะกำหนดการเปลี่ยนแปลงที่ต้องการดำเนินการกับฐานข้อมูล

ตัวอย่างการเปลี่ยนแปลง

สร้างตารางใหม่ (Create Table)

เพิ่มคอลัมน์ (Add Column)

แก้ไขชนิดข้อมูล (Alter Column)

ลบคอลัมน์ (Drop Column)

สร้างดัชนี (Create Index)

เพิ่มข้อกำหนดของข้อมูล (Add Constraint)

3. โครงสร้างไฟล์ Migration

ตัวอย่างโครงสร้างไฟล์

migrations/
├── 000001_create_users_table.up.sql
├── 000001_create_users_table.down.sql
├── 000002_create_servers_table.up.sql
├── 000002_create_servers_table.down.sql
├── 000003_create_metrics_table.up.sql
└── 000003_create_metrics_table.down.sql

หมายเลขด้านหน้าชื่อไฟล์ใช้ระบุลำดับเวอร์ชันของ Migration

4. Up Migration

Up Migration คือการนำการเปลี่ยนแปลงโครงสร้างฐานข้อมูลไปใช้ เพื่อปรับฐานข้อมูลให้เป็นเวอร์ชันใหม่

ตัวอย่าง

CREATE TABLE users (
    id UUID PRIMARY KEY,
    username VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL
);

5. Down Migration

Down Migration คือการย้อนกลับการเปลี่ยนแปลงของ Migration ที่เคยนำไปใช้ โดยย้อนกลับตามลำดับเวอร์ชัน

ตัวอย่าง

DROP TABLE users;

การย้อนกลับอาจทำให้ข้อมูลที่ถูกเพิ่มหรือแก้ไขในระหว่างนั้นสูญหาย จึงต้องตรวจสอบผลกระทบก่อนดำเนินการ

6. การจัดการเวอร์ชัน

ระบบจะบันทึกเวอร์ชัน Migration ล่าสุดที่ถูกนำไปใช้แล้ว เพื่อป้องกันการนำ Migration เดิมมาทำซ้ำ

ตัวอย่าง

Version 1: สร้างตาราง Users
Version 2: สร้างตาราง Servers
Version 3: สร้างตาราง Metrics

หากฐานข้อมูลอยู่ที่ Version 3 และสั่งย้อนกลับ 1 ขั้น ระบบจะย้อนกลับไปยัง Version 2

7. สภาพแวดล้อมการทำงาน

Migration สามารถนำไปใช้กับฐานข้อมูลในแต่ละสภาพแวดล้อมได้

Development: ใช้สำหรับพัฒนาและทดสอบการเปลี่ยนแปลง

Testing: ใช้ตรวจสอบความถูกต้องของโครงสร้างฐานข้อมูล

Production: ใช้กับฐานข้อมูลที่ให้บริการจริง

ทุกสภาพแวดล้อมควรใช้ชุด Migration เดียวกัน เพื่อให้โครงสร้างฐานข้อมูลสอดคล้องกัน

8. แนวทางปฏิบัติ

สร้างไฟล์ Migration ใหม่ทุกครั้งที่ต้องการเปลี่ยนแปลงโครงสร้างฐานข้อมูล

ไม่แก้ไขไฟล์ Migration เก่าที่ถูกนำไปใช้งานแล้ว

กำหนดหมายเลขเวอร์ชันให้เรียงตามลำดับ

เตรียม Up และ Down Migration ให้เหมาะสม

ตรวจสอบผลกระทบก่อนนำ Migration ไปใช้

สำรองข้อมูลก่อนดำเนินการเปลี่ยนแปลงใน Production

ไม่ใช้ Down Migration เป็นวิธีสำรองหรือกู้คืนข้อมูล

9. ผลลัพธ์ที่คาดหวัง

ฐานข้อมูลสามารถจัดการการเปลี่ยนแปลงโครงสร้างได้อย่างเป็นระบบ ตรวจสอบประวัติย้อนหลังได้ และสามารถนำโครงสร้างฐานข้อมูลไปใช้งานในแต่ละสภาพแวดล้อมได้อย่างสอดคล้องกัน

คำศัพท์ที่ควรรู้
คำศัพท์	ความหมาย
Migration	การเปลี่ยนแปลงโครงสร้างฐานข้อมูล
Schema	โครงสร้างของฐานข้อมูล
Version	หมายเลขเวอร์ชัน
Up	นำการเปลี่ยนแปลงไปใช้
Down	ย้อนกลับการเปลี่ยนแปลง
Rollback	การย้อนกลับ
Seed	การเพิ่มข้อมูลเริ่มต้น
Dirty State	สถานะ Migration ที่ทำงานไม่สมบูรณ์
